# Required Contract Tests (قبل أي دمج/Merge)

## 1. اختبارات بيانات (Data Contract Tests)
- [ ] إنشاء Book جديد يخزّن `purchase_price`/`shipping_cost` كـ Post
      Meta خاص، ولا يظهران في أي استجابة Frontend (تحقق آلي بفحص HTML
      الناتج لصفحة الكتاب — يجب ألا يحتوي القيمتين).
- [ ] `stock_quantity` بعد أي عملية (شراء/بيع/إرجاع/تالف/تعديل) يساوي
      تماماً مجموع `mkt_inventory_movements` لنفس `book_id`.
- [ ] كل Purchase مكتمل ينتج تلقائياً سطر Inventory Movement من نوع
      `PURCHASE` بنفس الكمية الإجمالية للبنود.

## 2. اختبارات انتقال الحالة (Domain Contract Tests)
- [ ] لا يمكن الانتقال من `NEW` مباشرة إلى `SHIPPED` بدون تسجيل سبب.
- [ ] الانتقال إلى `CANCELLED` قبل `SHIPPED` يعيد الكمية المحجوزة
      (سطر `RETURN` تلقائي).
- [ ] قياس SLA: كل طلب يحمل `contacted_at` بعد `created_at` عند
      الانتقال لـ `CONTACTED`.

## 3. اختبارات التكامل (Integration Contract Tests)
- [ ] رسالة WhatsApp المُنتجة لا تحتوي أي حقل من الحقول الداخلية.
- [ ] رابط WhatsApp يستخدم دائماً الرقم من `Admin/Settings`، وليس نصاً
      ثابتاً في الكود (تحقق: تغيير الرقم من الإعدادات يغيّر كل الروابط
      فوراً دون نشر كود جديد).

## 4. اختبارات الحدود المعمارية (Architectural Boundary Tests)
- [ ] فحص استيراد آلي (grep بسيط ضمن CI مستقبلي): لا وجود لأي
      `WC_` class أو `wc_` function خارج `Integrations/WooCommerce/`.
- [ ] فحص: لا وجود لأي `$wpdb` مباشر داخل `wp-content/themes/**`.
- [ ] فحص: لا تعريف مكرر لقوائم الحالات الثابتة (Order Status,
      Inventory Type) خارج ملفاتها المرجعية الوحيدة.

## 5. اختبارات القبول (من معايير V1 في المخطط الأصلي — Section 48)
- [ ] العميل يجد كتاباً بالبحث خلال 3 خطوات كحد أقصى من الرئيسية.
- [ ] إضافة كتاب جديد لا تتطلب تعديل أي ملف كود (فقط عبر لوحة الإدارة).
- [ ] نسخة احتياطية كاملة (DB + Files) قابلة للاستعادة فعلياً (اختبار
      استعادة تجريبي، وليس افتراض أن النسخ يعمل).
